## 2. 为什么重定位会提示两个 TF 树，重启几次又好了？

当前 Super-LIO 源码真实发布的是 `world -> imu`，不是部分旧文档写的 `map -> odom -> base_link`。

`test_demo/nav2_bringup.launch.py` 补齐两个静态变换，预期链路为：

```text
map --静态恒等--> world --Super-LIO动态定位--> imu --静态近似恒等--> base_link
```

Super-LIO 要先读取地图，再积累 IMU/点云做 NDT + ICP 初始化；成功之后才输出这段动态 TF。因此启动初期只有 `map -> world` 和 `imu -> base_link`，看到两个断开的树可能只是初始化尚未完成。初始化失败时缺失的动态边会一直缺失，反复重启只是重新进行匹配，不是修好了 TF。

已确认/值得优先排查的原因：

1. 地图未找到或地图不匹配：`super_lio_reloc.cpp` 从 `g_save_map_dir + g_map_name` 加载 PCD。初始化代码即使 `map_init()` 返回失败，仍会打印类似 “Map init success”，必须看前面的 `Load map failed/success`。
2. 初始姿态离默认原点太远：初始化默认猜测为零，不是任意位置都能可靠匹配。保持机器人静止，从建图起点附近启动，并检查 `Global ICP Converged Succeed/Fail`；必要时通过 RViz 的 `/initialpose` 给匹配初值。
3. 同时开建图、重定位、Odin 或另一份 Nav2，可能重复发布同名 TF 子节点。一个 TF 子节点不能有两个父节点，同一条边也应只有一个发布者。
4. 当前复制来的 `liblio.so` 内嵌路径是 `/home/slam/r2_ws/lidar_ws/src/Super-LIO/src/super_lio/`，当前目录却是 `/home/xiehan/桌面/r2_ws/...`。`ROOT` 来自编译时路径；只改 Python 路径或 source 新工作空间不会改掉它。在新机器部署需要在新路径重新编译 Super-LIO。
5. ROS_DOMAIN_ID、RMW、不同主机时钟不一致，或雷达数据未到，也会造成等待。TF 报错可能是定位失败的后果，不能仅凭“树断了”认定是 TF 发布器坏了。

本次导航节点使用 transient-local QoS 接收 `/tf_static`，可以读到它启动前已经发布的静态边；启动时等待完整 TF Buffer 可查询的链路，同时报告缺边和多父节点冲突。此检查不能证明 ICP 匹配到了正确位置，也不能识别同一条边的所有重复发布者。

## 3. 为什么避障卡住不动？是雷达还是局部规划器？

你的原版 launch 只启动 map_server、planner_server、lifecycle_manager 和静态 TF；没有 controller_server、BT navigator 或局部 costmap。原版全局 costmap 只有 static_layer 和 inflation_layer。

因此对你的版本而言，首先不是 DWB 局部规划器参数问题：实际根本没有启动它。Python 获取一次静态地图路径后，逐点发送速度，即使新障碍挡路也会继续向旧路径点运动，直到行走超时；原版没有较短的进度超时诊断。

另一个直接原因是 `livox_360.yaml` 的 `lio.sensor.blind: 2.0`：这是 Super-LIO 的软件过滤半径，2 m 内的点被滤掉。把 `/lio/cloud_world` 用于近场避障时，这会形成明显的近场缺口，不等于 Mid-360 硬件自身盲区有 2 m。

本次改为：

- Nav2 global costmap 同时使用静态地图、当前点云 obstacle_layer、inflation_layer，仍用原来的 Navfn 全局规划插件。
- `test_demo/relocation_params.yaml` 覆盖软件过滤半径为 0.3 m，并关闭定位地图保存与更新，保留建图使用的其他参数和外参。
- 点云保持 `world` 坐标，但 obstacle_layer 的 `sensor_frame` 指定 `imu`，让清除射线和观测距离从当前传感器位置计算。无需手工把 world 点云伪装成 base_link 点云。
- Python 在移动方向上检查点云，足够点数命中时停车，从当前位姿重新规划；每个目标最多三次路径尝试。定位或点云断流时停车报错。
- 5 秒内距当前路径点没有改善至少 2 cm，则停车并重规划，避免长时间顶住障碍。

这仍然是“全局规划 + 自己的路径跟踪 + 障碍停车后重规划”，不是完整 Nav2 局部动态轨迹避障。不会自动退让、倒车脱困，也不能保证高速或移动人群中的无碰撞导航。

点云停车检测默认：world z 0.15～1.8 m、侧向半宽 0.32 m、近场排除 0.30 m、前向检查到当前路径点并加余量（最多约 1.22 m）、同帧至少 3 个点。这些是初始参数，不是现场确认后的车体尺寸。world z 不是离地高度；当前 PCD 有负 z 地面点，需在 RViz 中实测地面高度后同时调整建图切片和导航高度范围，避免漏掉矮障碍或把自身回波当障碍。

避障卡住时按顺序判断：点云是否更新 → TF 是否完整 → costmap 是否画出障碍 → 是否存在足够宽的绕行路 → 是否规划成功 → TCP 通道是否发出 → 位置是否真的在改变。不要先盲目缩小膨胀半径；`robot_radius=0.30` 必须与实车包络吻合，长方形底盘最好改成实测 footprint。

## 4. 怎样控制位置误差小于 0.2 m、角度误差小于 1°？

原脚本最终位置阈值已经是 0.03 m，但角度阈值是 2°。如果终端显示位置误差很小，实测仍偏 0.2～0.3 m，问题更可能在地图匹配、坐标原点/外参、打点基准或停车后的滑移，而不是把到位阈值再改小即可解决。

本次保留 3 cm 的内部位置闭环目标，把内部朝向目标设为 0.8°；转向进入容差后停车并连续检查 0.4 秒，最终联合复核还要在停车 0.4 秒后再次读取定位。旋转造成平移漂移时最多三轮位置/朝向回正。建图打点采用 0.6 秒、至少三次不同更新时间的平均位置和圆周平均角度，拒绝过期定位、平移波动超过 3 cm 或角度波动超过 0.5° 的采样。

这不能保证外部真实误差：软件的 3 cm 是相对同一套 LIO 定位的误差，不是相对卷尺或场地标志的误差。最终验收必须在固定地图、固定车体参考点下独立测量，并测试重复重定位、不同朝向、前后与横移进入目标、转向后的漂移。

原有 `body_yaw_offset=180°`、`LATERAL_COMMAND_SIGN=-1` 是脚本记录的实车校准，本次保留。之前理想仿真假设 ch0 正值向左，与这个校准不一致，现已修正模拟器；不能用理想仿真替代硬件方向校准。现有 `imu -> base_link` 近似恒等也不代表真的完成了雷达到底盘中心的平移外参标定。必须确认点位代表雷达/IMU、底盘中心还是执行机构，不能把不同参考点的坐标混用。

低速空载测试建议每个点重复至少 10 次，分别记录外部位置误差、外部角度误差、终端误差、重定位成功率、障碍停车/绕行结果。单次最大误差也要满足位置 <0.20 m、角度 <1.0°，不能只报告平均值。

## 6. `lio.map.save_map: true` 会影响重定位吗？

会，有明确的源码依据。原 `super_lio/launch/relocation.py` 实际加载 `livox_360.yaml`，不是名字叫 `relocation.yaml` 的另一份文件。前者 `save_map=true`。`relocation_node.cpp` 退出时调用继承的 `saveMap()`，该函数受 `g_save_map` 开关控制，并可能使用 map/PCD 数据合并或写出地图。不能认为“指定固定文件名”就禁止了写回，恰好可能写同一个文件。

但不能把它直接说成所有 TF 失败的唯一原因：地图读取、ICP 成功和动态 TF 出现之间还有其他环节。

本次只让 `test_demo/nav.launch.py` 在原 `livox_360.yaml` 后加载独立覆盖文件，强制 `save_map=false`、`update_map=false`。建图继续用原配置保存；队友启动文件没有被最终修改。没有整份换用 `relocation.yaml`，因为两份配置的 `odom_robo`、output、滤波与容量参数不同，整份切换会影响已有坐标定义。

另移除了导航启动时自动修改共享 map.pcd 的步骤。原清理代码硬编码每点 16 字节，仅适合某种 PCD 布局，还不处理 NaN；启动时修改共享定位地图不利于复现。现有两份 PCD本次离线检查未发现上述坏点，所以不需要自动清理。

## 7. Nav2 是通过 cmd_vel 还是通道值控制下位机？

两者是不同层，TCP 最终都传协议通道值。

```text
你的 test_demo：
Nav2 ComputePathToPose → 路径 XY 点 → Python位置闭环
    → ch0横移 / ch2前后 / 当前yaw / 目标yaw → TCP V3帧 → 下位机

队友 ros2_ws：
NavigateToPose → Nav2 controller → /cmd_vel (Twist)
    → cmd_vel_bridge → ch0/ch2/yaw字段 → TCP V3帧 → 下位机
```

你的版本不订阅 `/cmd_vel`，不会因为修改 DWB、velocity_smoother 或 Nav2 goal_checker 就改变实际底盘跟踪行为。队友 bridge 的 `CH_SCALE_LINEAR=400` 将米/秒数值换成通道幅值，角速度通过 `cur_yaw + wz*YAW_GAIN` 转成期望角，不是标准电机驱动；这个比例必须实测。下位机协议目标 yaw 为 0 表示关闭航向 PID，所以真实 0° 用 0.01° 编码。

队友 DWB 配置的 `yaw_goal_tolerance=0.50` 单位为弧度，约 28.65°，明显不满足 1° 目标；另外 min_vel_x/min_vel_y=0 限制了反向动作。队友文件开头说使用静态地图，但后面的 global costmap 实际注释了 static_layer，并有 `/home/slam/...` 硬编码地图/脚本路径。需要修整后才能作为另一条完整导航路线。

严禁同时运行你的 TCP Sender、队友 cmd_vel_bridge、hand.py 或其他发帧控制脚本；两个控制来源会让动作结果无法解释。
